# Matrice des contrats de réservation

## Objet et méthode

Cette note est une cartographie de l'état observé au 2 septembre 2026. Elle
sert de base aux tests de caractérisation et ne désigne pas de
`ReservationService` canonique.

Le périmètre a été construit à partir des imports et appels trouvés avec
`rg`, puis vérifié dans les routes, les services et les tests. Les écritures
directes de `Reservation` qui contournent les deux classes `ReservationService`
sont également listées : elles sont nécessaires pour ne pas confondre
« caller du service » et « chemin réel de mutation ».

## Contrat Prisma commun

Le modèle `Reservation` contient deux colonnes distinctes :

- `status` : enum historique à quatre valeurs `CONFIRMED`, `CANCELLED`,
  `SEATED`, `NO_SHOW`, défaut `CONFIRMED` ;
- `state` : enum agentic à huit valeurs `PENDING`, `CONFIRMED`, `SEATED`,
  `HONORED`, `CANCELLED`, `NO_SHOW`, `FAILED`, `EXPIRED`, défaut `CONFIRMED`.

Les deux colonnes sont donc actuellement obligatoires et initialisées à
`CONFIRMED` par Prisma. La projection documentée dans le code ne couvre que
les quatre valeurs de `status`. Il n'existe pas de valeur historique pour
`PENDING`, `HONORED`, `FAILED` ou `EXPIRED`.

## Invariants réellement communs

Les preuves actuelles justifient ces invariants, indépendamment du service
qui deviendrait éventuellement canonique :

1. isolation stricte par `restaurantId` sur toute mutation et tout accès
   public/authentifié ;
2. validation de la taille du groupe, du créneau, de la policy et des limites
   d'exposition avant confirmation ;
3. une table ne peut pas être occupée par deux intervalles actifs qui se
   chevauchent ; les états actifs sont au minimum `PENDING`, `CONFIRMED` et
   `SEATED` dans le moteur capacity-aware ;
4. toute allocation concurrente doit être protégée par transaction + verrou ou
   par une contrainte/idempotence DB équivalente ;
5. un retry ne doit pas créer une seconde réservation lorsque le caller
   fournit la même identité de demande (`callId`, scope/key/hash, clé walk-in
   ou operationId selon le flux) ;
6. une annulation doit cesser de bloquer la capacité et doit conserver une
   trace compatible avec le niveau d'audit du flux ;
7. les projections `status/state` doivent rester alignées pour les quatre
   valeurs communes, sans inventer de projection pour les quatre états
   agentic sans équivalent ;
8. l'invalidation de disponibilité est best-effort mais doit suivre les
   mutations de capacité ;
9. les notifications et analytics ne doivent pas être confondues avec la
   transaction de réservation : elles sont post-commit et leurs échecs ont un
   contrat distinct.

## Divergences qui exigent une décision

Les différences sont assez importantes pour arrêter l'extraction de code dans
cette phase :

- `state=PENDING` peut coexister avec `status=CONFIRMED`, ce qui change les
  listes, rappels SMS et rapports historiques ;
- l'agentic garantit audit + idempotence + holds, tandis que le voice legacy
  garantit `callId` + Google Calendar + SMS ;
- l'annulation agentic et l'annulation legacy n'ont pas le même contrat de
  hold, d'audit et de notification ;
- au moins trois chemins créent encore directement des réservations
  (`waiting-list`, `walk-in`, `service-copilot-delay-recovery`) ;
- les services de disponibilité ne sont pas tous le même adapter et les
  traitements timezone diffèrent.

Il n'est donc pas justifié de choisir maintenant une source de vérité, de
fusionner les classes, ni d'extraire `VoiceLlmClient` ou des helpers de
`FloorPlanCanvas`. La Phase 2 s'arrête volontairement après la cartographie et
les tests de caractérisation ; aucune API, migration Prisma ou orchestration
de session n'est changée.

## Phase 3 recommandée

1. instrumenter les divergences `status/state` et les écritures directes
   (compteurs de mismatch par caller, état avant/après, capacité) sans changer
   le contrat ;
2. définir avec le produit la sémantique de `PENDING`, des états terminaux et
   des notifications ;
3. choisir deux ou trois scénarios de référence (Connect confirm, voice
   create, dashboard cancel) et exécuter les deux chemins en shadow/read-only
   sur des fixtures ;
4. décider quelles garanties doivent être communes (idempotence, audit,
   holds, Google/SMS) avant toute façade ;
5. seulement ensuite extraire un adapter LLM indépendant du manager, puis
   traiter les chemins de mutation directs et le découpage géométrique du
   canvas.

### Preuves de libération et états terminaux

- Le moteur capacity-aware et l'overlap SQL filtrent `state IN
(PENDING, CONFIRMED, SEATED)`. Les états terminaux agentic ne bloquent donc
  plus logiquement la capacité.
- `legacy.update(status=CANCELLED)`, `agentic.cancelReservation` et le revert
  copilot invalident ou réévaluent la disponibilité selon leur chemin ; une
  transitions agentic qui changent l'effet de capacité invalident maintenant le
  cache après commit.
- `delete` legacy libère par disparition de ligne, mais sans trace d'audit.
- `releaseTable` libère l'association physique sans changer l'état. La query
  capacity-aware exige `tableId` non nul, tandis que `findBlockingReservation`
  peut encore bloquer par restaurant, créneau et taille ; ce n'est pas encore
  une règle métier résolue.
- `state=PENDING/status=CONFIRMED` est observé à la création manuelle agentic,
  donc il bloque la capacité par `state` mais peut être compté comme confirmé
  par les lecteurs `status`.

## Preuve de capacité sans table — campagne Postgres

Le harnais `concurrency.test.ts` contient maintenant onze tests de
caractérisation supplémentaires, exécutés avec les migrations existantes sur
une base locale jetable puis supprimée. Pour `PENDING`, `CONFIRMED` et `SEATED`,
une ligne avec table bloque `CapacityAwareAvailabilityService`, tandis qu'une
ligne sans table est filtrée par `tableId IS NOT NULL`. Le prédicat
`findBlockingReservation` du service agentic bloque pourtant les trois états
sur le restaurant, la taille et l'instant exact, même sans table.

Les holds `ACTIVE` montrent la même différence de lecture physique avec/sans
table, alors que la contrainte globale `(restaurant, slot, party_size)` continue
de protéger la création d'un hold identique. `releaseTable` ne change que
`tableId` : la table physique redevient disponible, mais l'état reste actif et
le chemin agentic reste bloquant. Cette preuve ne tranche pas la capacité
globale versus physique ; la décision produit et le contrat de `releaseTable`
restent requis avant tout changement de prédicat.
