# Cartographie du runtime queues / schedulers

## Périmètre observé

Cartographie vérifiée le 2 septembre 2026 à partir de
`apps/api/src/shared/queue/queues.ts`,
`apps/api/src/modules/agentic-reservations/workers/queues.ts`, des imports de
`apps/api/src/main.ts`, des producteurs et des workers.

Toutes les queues BullMQ utilisent `redisQueue` (base Redis dédiée aux files).
Les workers sont actuellement importés par effets de bord dans le processus
API : démarrer `main.ts` démarre donc à la fois Fastify, les WebSockets, les
webhooks, les schedulers et les consumers. Aucun entrypoint PM2 n'est modifié
par cette phase.

Options communes observées :

- `defaultReliableJobOptions` : 5 tentatives, backoff exponentiel de 5 s,
  conservation de 1 000 succès, échecs conservés ;
- `highPriorityWebhookJobOptions` : 8 tentatives, backoff exponentiel de 2 s,
  conservation de 2 000 succès ;
- les queues best-effort/techniques ont leurs propres limites indiquées
  ci-dessous ;
- après le dernier échec, `setupWorkerListeners` tente de copier le job dans
  `dead-letter` avec données sensibles redacted.

### Runtime de réconciliation Phase 3D

Les cinq workers ci-dessus produisent `notification-status` dans la queue
`reconciliation` uniquement après un résultat `unknown`. Le job porte une
claim key déterministe, le provider, le canal et l'identifiant provider
disponible ; il ne contient ni téléphone, ni email, ni contenu de message.

Le worker de réconciliation lit d'abord la claim. Une claim `in_progress` est
laissée intacte pour éviter une course avec l'envoi initial ; une claim déjà
`success` est un no-op. Pour une claim `unknown`, le worker consulte Telnyx ou
Resend seulement si un identifiant provider et une API de lecture sont
disponibles. Une acceptation garde la claim en `success`, un refus certain la
libère, et tout résultat encore ambigu reste `unknown` puis rejoint
`dead-letter` via un job de revue manuelle au job ID stable. Cette branche
n'envoie jamais de message et ne modifie aucune réservation.

Les schedulers `daily-call-reconciliation` et `daily-sms-reconciliation` restent
inchangés : l'ajout de `notification-status` est déclenché par les workers et
ne crée ni fréquence ni entrypoint supplémentaires. Les providers exposent
une consultation pour les identifiants Telnyx/Resend retournés ; si cette
information manque, la réconciliation automatique est impossible et le cas
reste explicitement manuel.

## Validation Phases 3C/3D

Les garde-fous de notification ont été vérifiés par des tests unitaires avec
Redis et providers fakes ; aucune requête provider réelle n'a été exécutée.
La base Postgres de validation Phase 3C était locale, dédiée et jetable ; elle

restent des résultats inconnus : ils conservent la claim, sont réconciliés par
lecture seule lorsque possible et rejoignent la revue manuelle sinon. Les
workers non couverts par les claims restent hors périmètre commercial.

## Phase 3E — clôture opérationnelle sans nouveau scheduler

Le job scheduler `daily-sms-reconciliation` existant effectue désormais aussi
un balayage borné de l'espace Redis `notification:*`. Cette réutilisation ne
change ni sa fréquence, ni son nom, ni son entrypoint. Une claim versionnée
`in_progress` est active pendant 15 minutes ; au-delà, elle est récupérée par
CAS tokenisé vers `unknown`, puis un `notification-status` est ajouté avec un
`jobId` déterministe. Le balayage ne fait jamais d'appel d'envoi.

La branche de réconciliation prend un lease atomique avant toute lecture
provider. Une acceptation provider déclenche seulement la réparation
idempotente d'un audit ou marqueur déjà existant ; waiting list et call recovery
n'ajoutent pas de nouvel audit sans décision produit. Une absence d'identifiant,
d'API de lecture, de réponse cohérente ou de réparation locale rejoint la
revue manuelle, avec la claim conservée lorsqu'un envoi peut être ambigu.

Un refus certain observé directement par le worker relance le job source BullMQ
déjà configuré, avec son payload original et ses bornes de tentatives ; aucune
queue de retry parallèle et aucun payload PII ne sont créés. Si le refus
certain n'est établi que par une lecture de réconciliation après un
`unknown`, la claim est libérée pour revue manuelle : elle ne contient pas le
payload source nécessaire à un rejeu sûr. Un résultat `unknown`, une erreur de
queue ou une indisponibilité Redis n'autorise jamais un nouvel envoi automatique.
Les
metrics `sokar_notification_claim_events_total` exposent seulement des
événements à faible cardinalité (`active`, `orphan_recovered`, `manual_review`,
`raced`, `unknown_requeued`, `queue_unavailable`, `scan_unavailable`,
`scan_failed`).

La validation Telnyx/Resend de cette phase est limitée aux fixtures et
normaliseurs testables ; aucune autorisation de staging n'a été fournie et
aucun provider réel n'a été appelé. Le statut commercial reste **NO-GO**.
